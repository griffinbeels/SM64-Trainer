# Tuning demos: any surface, tunable like a Godot Inspector

The human judges feel; I cannot. A loop where I pick a number, he watches it and
reports a verdict is the slowest possible way to find a value that needs ten
guesses — and it is *wrong* as often as it is slow, because a curve judged by
watching is judged from its middle. He said how he wants to work instead:

> "for any animations / any 'feel' based things like this in the future, this is
> how I would like to work with you. Basically like how I would work with an
> Inspector in Godot, I want to be able to tune all of the variables that
> determine the animation, get it to how it feels good for ME, and then tell you
> what we want to codify for the actual settings." (2026-07-27)
>
> "I'm imagining a world where each of the cards we have on screen, since we've
> designed our system that way, can therefore be extracted into this type of
> demo."

**Build the rig before the values.** The tuned numbers are the *output* of the
session, not the input.

Worked example, and the thing to copy: `ui/climbtuning.js` + `ui/tune.html` +
`ui/tune.js` + `server/tuning_api.py`, for the rank-up climb.

## What makes a surface extractable

Four properties. A surface that has them costs an afternoon; one that lacks
them costs a refactor first, and **the refactor is worth doing anyway** — each
of these is independently good design.

1. **The numbers live in ONE registry, not as constants.** One row per tunable
   carrying the shipped default plus `group`/`label`/`min`/`max`/`step`/`unit`/
   `why`. The registry is the single source: the app reads it, the inspector
   generates its controls from it, and SAVE writes back into it. Import-free so
   node can drive it.
2. **Consumers take the config as an ARGUMENT, defaulting to the registry.**
   `barSweepMs(divisions, tuning = DEFAULTS)`. They stay pure and unit-testable,
   behaviour with no config is exactly what ships, and the inspector can drive
   them without touching global state. Only the top-level wiring reads the
   active slot, and it reads it **once per run** — a tuning change mid-flight
   retimes an animation that is already half-played.
3. **The component takes PROPS, not the store.** This is the one that bites.
   `RankBanner` takes a `banner` object, so the demo mounts the real thing; the
   objective card *around* it is welded into `practice.js` behind a live store,
   so the demo had to replicate its chrome from the app's own CSS classes. That
   replica is a standing gap, written down in `.claude/rules/ui.md`. **When you
   extract a card for a demo, first check whether it can be made presentational
   — a component that takes props is the whole ballgame**, and it is the reason
   his "every card can be extracted" vision is reachable at all.
4. **The page wears the REAL stylesheet.** Fetch `index.html` at runtime and
   inject its `<style>` block; never copy it. A stylesheet that had drifted by
   one value would make the page judge something other than the app, which is
   the only way this whole exercise can quietly become worthless.

## The recipe

1. **Registry** — `ui/<surface>tuning.js`. Copy `climbtuning.js`'s shape:
   `TUNABLES`, `CHOICES`, `DEFAULTS`, `GROUPS`, `withDefaults`, the active slot
   (`tuning`/`setTuning`), `encodeTuning`/`decodeTuning`/`changedFromDefault`.
   Ranges deliberately wider than sensible — a value has to be pushed past good
   to find out where good was.
2. **Thread it** — every consumer gains a `tuning = DEFAULTS` parameter. Do not
   let a consumer read the active slot; that is the wiring layer's job.
3. **Page** — `ui/tune-<surface>.html` + `ui/tune-<surface>.js`, copied from the
   climb pair. Controls are generated by looping `GROUPS` × `TUNABLES`; you write
   no per-control code, ever. Served by the existing `/ui` static mount — no
   server route needed for the page itself.
4. **Save** — add one row to `TUNING_REGISTRIES` in `server/tuning_api.py`
   mapping your surface name to its registry file. `POST /api/tuning/<name>`
   then rewrites its `value:` fields. Nothing else to write: the endpoint
   validates against the file's own `min`/`max`/`options`, can only replace a
   `value:` that already exists, and refuses when frozen.
5. **Reachability** — link it from the settings drawer with an **origin-relative**
   href, and print it in `run-test-server.bat`. A dev page behind a hand-typed
   path is a page that does not exist; this one went missing on day one because
   the only written-down URL named a port the launcher had already changed.
   Pinned by `tests/test_header_ui.py`.
6. **Show what will actually play.** A readout of the resolved plan/state, live
   as the sliders move, plus a named warning wherever a control's number is not
   the number that runs. See the trap below for why this is not optional.

## Three traps, each paid for once

**A floor may never override the ceiling above it.** `max(floor, min(ceiling,
wanted))` puts the floor OUTSIDE, where it silently outranks a value the user
just set — a 100ms step against an untouched 220ms floor ran at 220 at every
step count while the slider read 100, and a whole session was judged against a
number nothing was displaying. Use `min(ceiling, max(floor, wanted))`
(`climbcurve.js::floored`) and pin it with a property test over the whole
floor/ceiling/budget space **plus its inverse**, so the fix cannot rot into
"delete the floor". Legitimate clamps remain — that is what step 6 is for, and
a per-control "effective" badge is the wrong answer because it has to re-derive
the arithmetic that caused the discrepancy.

**Once SAVE writes the defaults, no test may assert one.** Those values belong
to whoever last used the inspector; eight tests went red the first time he
tuned. Pin the LAW against an explicit `REFERENCE` tuning defined in the test
file, and let a separate test check only that the live values are coherent and
in range. A choice-valued test must flip to whichever option is *not* currently
stored.

**Two guards, or the rig lies.** Both mutation-proved, both in
`tests/test_ui_climbtuning.py`:
- every tunable must be READ by a consumer — a row nobody reads is a slider
  that changes nothing, and the inspector draws it just the same;
- no consumer may read a key the registry lacks — `undefined` becomes a NaN
  duration, i.e. an animation that never ends, which only a hold ceiling would
  ever notice.
Plus a golden test that the config-with-DEFAULTS result is byte-identical to
the no-config result, and its inverse proving a changed value actually moves
the output — so neither can pass by accident.

## Verifying the page

`--dump-dom` renders but cannot drive, and `requestAnimationFrame` **never
fires** under `--virtual-time-budget`, so a Preact app dumped that way renders
almost nothing and reads exactly like a broken feature. Serve the real `ui/`
from a scratch static server, inject a driver that swaps rAF for `setTimeout`
and clicks the page's own controls, and read results out of an output element —
never out of the dump, which echoes the driver's own source. Measure boxes
(`getBoundingClientRect`) rather than asking whether text is present: a
`textContent` probe matched the driver script's own string literal and reported
a closed drawer as open.

Then **look at the screenshot**. A metric answers "is something there", never
"does it read as the thing you meant" — the first render of the climb page put
the card 65px over the panel and covered its text, with every count green.
