| MARELO scope surface (aggregate/history/exclude/ack) | `server/ranks_api.py` (same file, built on top of the ranks CRUD above — scoring/aggregation itself lives in `ranks/scoring.py`+`ranks/scopes.py`+`ranks/history.py`+`tracking/marelo.py`, see `.claude/rules/ranks.md`) — `GET /api/marelo` (`?scope=`, defaults to `_active_scope` = the focus route else Overall, so there is no second scope control to keep in sync; unknown scope → `404` deliberately, so a stale route id in a client reads as gone rather than silently becoming a different rating), `GET /api/marelo/history`, `GET /api/marelo/scopes`, `GET /api/marelo/summary` (the always-visible op.gg-style chip row: `overall` + every `category`-"Main Categories" route + the active scope, capped at 6 — `_score_scope` factors the pure groups→aggregate→per-entity-tier path OUT of `_build_marelo` specifically so this endpoint can reuse the scoring without also running `_build_marelo`'s watermark side effects; loops `_score_scope`, never `_build_marelo`), `POST /api/marelo/exclude` (reversible — excluded entities stay in the response's `entities` as inert rows: `_append_excluded_rows` re-resolves scope membership a SECOND time with NO exclusion filter to find them again for display, without letting them back into `aggregate`'s numerator/denominator), `POST /api/marelo/ack` (body takes EITHER `{scope,key}` OR `{entity,key}` — exactly one, `400` otherwise — routing to `ack_celebration` or `ack_entity_celebration`). Three distinct watermark operations, all in `_build_marelo`/`TrackerService`: `ack` RAISES (UI-driven only — fired once the celebration has actually been shown, never on a bare GET), `sync_watermark` LOWERS on every GET (follows a drop down so re-climbing celebrates again), `seed_watermark` CREATES on a scope's first-ever rank (no-op once the key exists, so the first view of a scope never celebrates the user's whole history at once) — `/api/marelo/summary` triggers NONE of these three, by construction (`_score_scope` never calls them). `marelo_changed` is broadcast-only (no journal entry). **Entity-level celebrations** (task-f1, 2026-07-25): `_build_marelo`'s payload also carries `entity_celebrations` — a list, not a single value, since more than one entity can cross a tier between two views. `_entity_scores` scores the FULL rankable corpus (reuses the `overall` scope's own group resolution, which already IS every rankable entity — no second scoring pipeline); `_entity_celebrations` applies the same sync→read→seed dance as the scope path but through ONE batched service call, `TrackerService.sync_and_seed_entity_watermarks` — a per-entity get_state/set_state (the scope path's shape) would cost up to ~200 sqlite commits per request across ~102 entities, so the batch call round-trips the watermark dict ONCE (one read, at most one write) regardless of corpus size. Entity watermarks live under their own `ui_state` KV (`entity_rank_watermarks`, via `TrackerService.entity_watermarks()`), never merged into `marelo_watermarks` — scope ids and entity keys don't collide by prefix today, but a second KV makes that true by construction. `_build_marelo` reuses `out["entities"]` for the corpus when `scope_id=="overall"` (free) and pays one extra `_score_scope("overall")` call (~2-3ms measured over the bundled 102-entity seed) for any other scope — see task-f1's report for the full measurement. `/api/marelo/summary` never touches entity watermarks either, by the same construction as the scope guarantee. |
