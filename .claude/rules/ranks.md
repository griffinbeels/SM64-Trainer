# Ranks — where to change what

| To change... | Edit |
|---|---|
| Rank classification (pure) | `ranks/classify.py` — THE rank ORDER (Mario..Iron) + RANK_SCORE + display_cs/rank_for/next_tier/band; compares DISPLAYED centiseconds so rank never disagrees with the shown time; Iron is the unbounded FLOOR (no threshold, never settable — `standards.set_threshold` rejects it), so its bar cannot measure from a start: it fills ASYMPTOTICALLY, `easiest_cutoff / time` — 1.0 AT that cutoff, decaying, never 0. Same curve as `ranks/scoring.py`'s Iron tail ON PURPOSE, so bar and MARELO score never tell one run two stories; a flat 0% means "never attempted", never "slow" (user decision 2026-07-25); ALSO `resolve_cutoff_videos(ladder_cs, clips, overrides)` — bands timed example clips into `{rank:url}` (fastest per tier, via the SAME rank_for; user overrides win); ALSO `RANK_MODES` (pb/avg10/avg50/best10/best50/lifetime) + `average_frames` — THE rank-mode registry (average mode: entity-level medals grade the mean of valid runs — successful, uncleared, strat-tagged, timed; views.py `_grading_basis` is the ONE resolver; per-attempt medals stay per-run) |
| Rank standards store (editable JSON, seeded) | `ranks/standards.py` over `data/rank_standards.json`; entity_key; seed/corrupt→empty fallback; CRUD; per-cutoff videos: `clips()` (auto, from seed) + `user_videos()` (hand-attached) merged by `cutoff_videos(ek, extra_clips=None)` — `extra_clips` is `library/examples.py`'s per-strategy library pool (task 0098), merged BEFORE banding so the fastest in-band example wins whichever source it came from; `set_video`/`clear_video` write overrides under the entity's `user_videos`, which `_reconcile` preserves across a seed bump; `seeded_strategies` = the custom-vs-default distinction. **Exit-star variants (100-coin stars, spec 2026-08-03-hundred-coin-exit-variants)**: `VARIANT_SEP`/`qualify` own the qualified name (`100c + Race · Standard`) and `exit_variants` is ONE map, label→exit star — one, not two, so the heading a strategy is grouped under and the exit star it is classified by are the same fact and cannot disagree. `variant_of` splits by longest prefix; `strategy_groups` is the grouped view the API and the session view both ship (the browser never re-derives it); `exit_star_options` lists every ending with its label or null; `create_strategy(ek, strat, exit_star)` MINTS a variant for an unlisted ending and RETURNS the stored name. `_reconcile` preserves user-minted variants alongside user-created strategies. The qualification is forced, not stylistic: CCM publishes two 100-coin ladders and both define "Standard" AND "Open", so a bare name cannot identify a ladder there. Tier COLOUR left this module 2026-07-25 — the old `RANK_COLORS` dict had no runtime consumer, existing only to be mirrored into JS; it is now `ui/components/caps.js::CAP` alone (`.claude/rules/ui.md`'s Cap icon row) |
| Rank standards scraper | `tools/scrape_ranks.py` — fetches the xcams Next.js chunk, extracts the embedded JSON.parse standards blob, maps keys→entities, writes `src/sm64_events/data/rank_standards.seed.json`; emits per-strat `videos` (primary) + `clips` (ALL timed cams via `strat_clips`, for band resolution); `SEED_VERSION` gates reconcile (now 5); re-run to refresh. **100-coin keys** (`<stage>_100c<N>`, stages 0-14) map to that course's 100-coin STAR (`star:<course>:6`), N being the 1-BASED exit star; all 19 were silently dropped until 2026-08-03 because `key_to_entity` read the star part with `str.isdigit()`. Several keys therefore map to ONE entity, so `build_seed` MERGES rather than assigns — each variant's strategies (and its videos/clips/jp deltas) are renamed through `qualify` with the variant's label, taken from xcams' own catalog short name (`100c + Slide`) and falling back to our star registry. A label claiming two exit stars, or two ladders colliding on one stored name, RAISES rather than overwriting. `tests/test_hundred_coin_screenshots.py` pins the result against the user's own 18 captures of the xcams tables — the one check independent of our parser, since the site and the scraper read the same blob. Bowser keys map three ways — `<n>n`→pipe segment (No Reds), `<n>x`→fight segment (Battle), `<n>r`→the COURSE'S 8-red-coin star (`_BOWSER_REDS`, star:16/17/18:0; missing this dropped every reds ladder). `tests/test_scrape_ranks.py` pins the bundled seed's nine-Bowser-target coverage — a mapping hole is invisible in unit tests, only the OUTPUT shows it |
| The 0–100 curve, divisions, best-possible ladder (**MARELO**, spec 2026-07-24-marelo-rank-system) | `ranks/scoring.py` — `SCORE_ANCHORS` are xcams' own player bands verbatim (+ a Bronze anchor at 10, so the Iron tail owns its own decade). THE invariant: `tier_from_score(score_for(L, t), defined_tiers(L)) == classify.rank_for(L, t)`, pinned over all 278 seeded ladders by `tests/test_ranks_scoring_seed.py`. `defined_tiers` is REQUIRED for entity-level lookups — a ladder missing a tier still crosses that tier's score range, so a full-table lookup would name a tier the ladder does not define; omitted only for aggregates, which have no ladder. `best_ladder` pointwise-mins `{strat:{rank:seconds}}` into one ladder in CENTISECONDS — "the best time achievable at this tier by any known strategy", what an entity's own score grades against (so mastering a slow strat maxes the strat's rank without maxing the star's). `division_for` slices each tier into 5 equal score-width `DIVISION_NUMERALS` (V at the bottom); `progression_key` is the monotone rank ordering the celebration watermark stores (Iron V = 0). **`progress_for_time(ladder_cs, time_cs)`** (2026-07-29) is the TIME-aware sibling of `division_progress` and the one place the displayed-centisecond boundary rule lives — a step is reached when the displayed time reaches that step's own displayed cutoff, `<=`, exactly the rule `classify.rank_for` already applies at a tier cutoff. It exists because a division edge is interpolated and so lands at a FRACTIONAL centisecond that `time_for_score` rounds to report: comparing exact score against a rounded time told a run half a centisecond short that it owed `0.00s to rank up` (live report; 3,656 (ladder, time) pairs across the 278 seeded ladders hit it — see docs/architecture.md for the measurement). It raises `score` alongside the division so the payload cannot contradict itself, returns `next_gap_cs >= 1` whenever a next step exists, and cannot move a TIER on its own (a tier edge is an anchor, which `time_for_score` returns exactly). `views.py::_graded_progress` is a thin adapter over it now — it owns only the `rank` key. Guarded by `tests/test_ranks_scoring.py` + `tests/test_ranks_scoring_seed.py`, both mutation-proved |
| Scopes + aggregation (**MARELO**) | `ranks/scopes.py` — a scope is a derived SET; every route in the library, including user-created ones, is therefore automatically a rating with its own history — there is no scope registry to maintain. `entity_groups` resolves a scope into GROUPS (`{"need": k, "candidates": [...]}`) so a route's K-of-N step contributes k slots scored by its best k candidates, the same best-K convention `tracking/routes.py` already uses. `aggregate` is `MARELO = mastery × coverage`: ABSENT (no ladder — never enters `rankable_entities`) vs ZERO (rankable, unpracticed — no key in the scores map) is load-bearing; `practiced` counts by a key's PRESENCE in the scores map, never truthiness, so a genuinely-scored 0.0 still counts (regression-tested). `gain_for` is the MARELO an entity's next tier is worth, diluted by the scope's total slot count; unpracticed entities target Gold rather than Iron so they read as real quests, not floor entries. `celebration_delta` fires only on a RISE against the stored watermark — a drop is handled by the caller lowering the watermark silently, so re-climbing celebrates again; a first-ever rank (watermark `None`) is never a celebration |
| Rank history (**MARELO**) | `ranks/history.py` — recomputed, never stored: `history_series` replays successes chronologically, applying the active rank mode's window per (entity, strategy), taking the best strategy per entity, and re-aggregating after every success — so history follows CURRENT standards and CURRENT route membership by design (a seed bump or a route edit retroactively reshapes the past; the UI states this rather than hiding it). Pure — the caller injects `entity_scorer`, so this module never touches the standards store. `_decimate` always keeps the newest point so the chart ends on the current rank. In `pb` mode the feed is `marelo.pb_feed` (saved pbs), not `successes_for` — the curve must come from the same source as the rating or its last point disagrees with the card |
| Attempts → per-entity scores (**MARELO**'s rank-mode basis) | `tracking/marelo.py` — takes the active rank mode's basis — in `pb` mode the SAVED pb row via `views.current_pbs_by_strat` (`_pb_scores`), otherwise the averaging window's mean over attempts (`_average_scores`, the batched-over-entities sibling of `views.grading_basis`). It took `min()` over raw attempts until 2026-07-28 and so awarded MARELO before the user clicked Save as PB (task 0034); `undo_pb` deletes the row, so taking the points back needs no code of its own. `pb_feed` is the pb-mode sibling of `successes_for` and feeds `ranks/history.py`, which takes the LATEST entry in pb mode rather than `min` — latest-row-wins is the pbs contract. Pinned by `tests/test_single_source.py`. `entity_scores` omits entities with no gradeable time — ABSENT, never zero; `ranks/scopes.py::aggregate` supplies the zero, because only it knows the denominator |
| MARELO REST + exclusions + celebration ack | `server/ranks_api.py` — see the server-layer rule file (`.claude/rules/server.md`) for the endpoint list; the short version is the focus route IS the scope, an unknown scope 404s deliberately, and exclusion is reversible from the UI |
