| The 0–100 curve, divisions, best-possible ladder (**MARELO**, spec 2026-07-24-marelo-rank-system) | `ranks/scoring.py` — `SCORE_ANCHORS` are xcams' own player bands verbatim (+ a Bronze anchor at 10, so the Iron tail owns its own decade). THE invariant: `tier_from_score(score_for(L, t), defined_tiers(L)) == classify.rank_for(L, t)`, pinned over all 278 seeded ladders by `tests/test_ranks_scoring_seed.py`. `defined_tiers` is REQUIRED for entity-level lookups — a ladder missing a tier still crosses that tier's score range, so a full-table lookup would name a tier the ladder does not define; omitted only for aggregates, which have no ladder. `best_ladder` pointwise-mins `{strat:{rank:seconds}}` into one ladder in CENTISECONDS — "the best time achievable at this tier by any known strategy", what an entity's own score grades against (so mastering a slow strat maxes the strat's rank without maxing the star's). `division_for` slices each tier into 5 equal score-width `DIVISION_NUMERALS` (V at the bottom); `progression_key` is the monotone rank ordering the celebration watermark stores (Iron V = 0). **`progress_for_time(ladder_cs, time_cs)`** (2026-07-29) is the TIME-aware sibling of `division_progress` and the one place the displayed-centisecond boundary rule lives — a step is reached when the displayed time reaches that step's own displayed cutoff, `<=`, exactly the rule `classify.rank_for` already applies at a tier cutoff. It exists because a division edge is interpolated and so lands at a FRACTIONAL centisecond that `time_for_score` rounds to report: comparing exact score against a rounded time told a run half a centisecond short that it owed `0.00s to rank up` (live report; 3,656 (ladder, time) pairs across the 278 seeded ladders hit it — see docs/architecture.md for the measurement). It raises `score` alongside the division so the payload cannot contradict itself, returns `next_gap_cs >= 1` whenever a next step exists, and cannot move a TIER on its own (a tier edge is an anchor, which `time_for_score` returns exactly). `views.py::_graded_progress` is a thin adapter over it now — it owns only the `rank` key. Guarded by `tests/test_ranks_scoring.py` + `tests/test_ranks_scoring_seed.py`, both mutation-proved |
| Scopes + aggregation (**MARELO**) | `ranks/scopes.py` — a scope is a derived SET; every route in the library, including user-created ones, is therefore automatically a rating with its own history — there is no scope registry to maintain. `entity_groups` resolves a scope into GROUPS (`{"need": k, "candidates": [...]}`) so a route's K-of-N step contributes k slots scored by its best k candidates, the same best-K convention `tracking/routes.py` already uses. `aggregate` is `MARELO = mastery × coverage`: ABSENT (no ladder — never enters `rankable_entities`) vs ZERO (rankable, unpracticed — no key in the scores map) is load-bearing; `practiced` counts by a key's PRESENCE in the scores map, never truthiness, so a genuinely-scored 0.0 still counts (regression-tested). `gain_for` is the MARELO an entity's next tier is worth, diluted by the scope's total slot count; unpracticed entities target Gold rather than Iron so they read as real quests, not floor entries. `celebration_delta` fires only on a RISE against the stored watermark — a drop is handled by the caller lowering the watermark silently, so re-climbing celebrates again; a first-ever rank (watermark `None`) is never a celebration |
| Rank history (**MARELO**) | `ranks/history.py` — recomputed, never stored: `history_series` replays successes chronologically, applying the active rank mode's window per (entity, strategy), taking the best strategy per entity, and re-aggregating after every success — so history follows CURRENT standards and CURRENT route membership by design (a seed bump or a route edit retroactively reshapes the past; the UI states this rather than hiding it). Pure — the caller injects `entity_scorer`, so this module never touches the standards store. `_decimate` always keeps the newest point so the chart ends on the current rank. In `pb` mode the feed is `marelo.pb_feed` (saved pbs), not `successes_for` — the curve must come from the same source as the rating or its last point disagrees with the card |

## The Scorecard's rows, goals and exclusions

SCOPE-DRIVEN since round 6 (2026-08-24, "whatever is in the scope is what we generate a scorecard for"): `ranks/scorecard.py::template_rows(fight_segments=)` (Overall — 15 course rows of SIX cells, a **Bowser Fights row** when fight segments exist — category "Bowser Fights" — and the Secret row: 15 entries since round 9, the three Bowser REDS stars ("not the BitS entry for now"), PSS ×2, SA, the caps, WMotR AND the castle's Toad ×3 / MIPS ×2, so the card collectively holds all 120 stars), `rows_for_route(route, segment_labels=, segment_courses=, fight_segment_ids=)` (round 9 REPLACED step-group rows: every entity BUCKETS to its course's row / the Fights row / the Secret row, first-touch order, courses then Fights then Secret — his reference sheet's shape, "Course Cards + one secret card") and `rows_for_course` (`course:0` = the five castle-secret stars) feed `build_card(rows_spec, you=, goal=)`. THE CELL RULE is `hundred_coin_companion` + `_merge_hundred_coins`: a course's 100c star combines with its companion (default = the star named "Red Coins"; five exceptions store his verbatim names, resolved against STAR_NAMES at import, RAISING on a rename — `tests/test_scorecard.py::HIS_PAIRINGS` is the independent verbatim copy), wherever a row holds both; the old `fold`/`folded` machinery is DELETED, not disabled. **`scoring.best_ladder` repairs its own minimum** (round 14): the pointwise min over strategies with DIFFERENT tier sets is not monotone -- a sheet-fitted "advanced" strategy that skips Silver gave `star:1:5` a Bronze cutoff FASTER than its Silver, which no score curve can invert, so the card printed "set a time…" on stars with full published standards (measured on his own store: 3 of 117 graded entities, two of them the ones he reported). A cutoff may never be faster than a harder tier's, so the min is clamped fastest-first; the old docstring's claim that "the min of monotone ladders is monotone" was true only for equal tier sets. `division_goal_cs` inverts a ladder's score curve to the slowest cs that grades AT LEAST `(tier, division)` — "at least" since round 12 (2026-08-29): near the top a division can span zero integer centiseconds (his ladders put 3cs across Get a Hand's whole Metal tier), and four live tiles read "set a time…" until the snap; None only for a tier the ladder does not define (the seed sweep test pins zero holes); `_sum_tiles` counts only both-sides tiles, `total` stays the row's raw count for the coverage chip. `server/scorecard_api.py::create_scorecard_router` owns the persisted goal (`ui_state` KV `scorecard_goal`) and the four routes (`GET /api/scorecard?scope=`, `PUT /api/scorecard/goal`, `GET /api/scorecard/column`, `GET /api/scorecard/export.csv?scope=`); `current_card(scope_id)` is the one door both the GET and the CSV export build from, and `scope_rows` 404s an unknown scope exactly like `/api/marelo`. **The card drops exactly what the scope's RATING drops** (round 7, 2026-08-28: *"This should match the route include/ignores logic"*) — `scorecard.without_keys(rows, service.rank_excluded())`, the same resolved set `_score_scope` filters, so a movement the route rating ignores draws no cell and a step that was only such movements draws no row; an explicit include through `POST /api/marelo/exclude` puts it back. Never a second exclusion rule here: a card grading a movement its own rank ignores would be scoring a different route than the number beside it. A FOURTH goal kind, `multi` (round 14, 2026-08-31, his design: *"what if we could select multiple options... Then, we should take the MAX TIME from all of those players"*), is a LIST of goals in their own shapes, resolved through `resolve_goal` -- one recursive resolver for every kind, so a source is validated and read exactly as a single pick of that kind is -- and merged by keeping the SLOWEST offer per entity: the goal stays beatable, and coverage is the UNION, which is how several runners cover the stars none of them covers alone. Sources are structured, never the picker's `"division:Bronze:I"` value strings, because a string would need the same parser in JS and again in Python. A THIRD goal kind, `custom`, is hand-typed per-tile times a player saved under a name in a second KV (`scorecard_custom_goals`, `{name: {entity_key: goal_cs}}`) that `scorecard_goal` only ever points at by name — the one kind `current_card()` resolves with no `service.ranks` lookup at all, and picking a saved one is the same one-line KV write as picking a division. Round 11 (2026-08-28): `scopes.UNTRACKED_CASTLE_STARS` (star:0:0..4, the Toad/MIPS stars) joined `default_excluded` — *"nobody wants to track [them]... ignored in everyone's trackers"* — so they leave the default card AND every rating; an explicit include restores them to the Secret row (`test_castle_stars_are_off_the_card_until_included`). They are also 5 of the 6 entities the community standards store has NO ladder for (measured; the 6th is Slide Star (Under 21 Seconds)) — the "set a time…" tiles he asked about, which the in-place custom editor exists for. Tiles also carry `strat` (the ACTIVE strategy via `ActiveStrats`, `_stamp_strats`) so the card's library doors land on the practised approach. Tiles also carry `you_rank`/`goal_rank` (round 9): `scorecard_api._grade_tiles` stamps each side's `{tier, division}` against the entity's best ladder server-side — the card only DRAWS caps, so it can never grade differently than the Rank tab; `_tile` emits both as `None` and `scorecardgoal.js::_recomputeTile` nulls `goal_rank` on an unsaved in-place edit, which is what keeps the JS/Python parity test exact. On the card itself (`ui/components/scorecard.js`, round 9's grid — nothing expands any more), a line's Goal time edits in place — recomputed live client-side (`scorecardgoal.js::applyGoalOverrides`, mirroring `_tile`/`_sum_tiles` line-for-line, no round trip per keystroke) until "save as" writes it through `PUT /goal {kind:"custom", name, times}`, which both stores and activates it in one call.
