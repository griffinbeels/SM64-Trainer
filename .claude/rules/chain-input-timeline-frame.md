# Chain: which game frame the paused video picture shows, and the pad the panel draws for it

Read this before editing any module named below. A symptom is seen at the
SINK; its cause sits at the FIRST hop where the value stops being true, and a
fix downstream of that hop cannot hold. Before any fix: run the counterfactual
(force the known-good value in at a hop, re-run to the sink, see whether the
symptom vanishes) — the earliest hop whose correction prevents the failure is
the one to fix. Walk the table only when the counterfactual is ambiguous.

- **Value:** the game frame a video picture shows, and therefore the pad the input timeline's panel draws beside that picture.
- **Source truth:** Usamune's own input display, painted INTO every picture (his ruling: the screen is the truth); the pad per game frame in RAM, read by the sampler at 250 Hz (`InputSampler.health()["edge_mismatches"]` is its self-check).
- **Sink:** the panel under the timeline (FRAME n / N, the stick box, the button chips) on the picture the `<video>` is presenting.
- **One clock:** the picture feed (item 38, 2026-09-02) puts hops 4-7 on the pictures' own composition times -- seconds since the run's spawn, carried in the clip as `frame_times` -- so a frame's time in the browser IS the time the ledger stamped it and hop 5 is bookkeeping. The CFR feed (clips from before it, the in-process fallback, `picture_feed=False`) has no one clock end to end: hops 1-3 run on the GAME frame counter, hops 4-6 on wall-clock capture time and a 60 Hz encode grid, hop 7 on the browser's `mediaTime`, joined only by the inferred map.

## Counterfactual recipe

For a report of the shape "the screen shows X, the panel shows Y on the same
paused picture":

1. Hop 3: build the payload offline with the clip's span and read the run at the
   panel's axis. If it holds Y where hop 2 holds X, the fault is the run
   collapse or the axis; stop there.
2. Hop 5: `tools/score_pad_read.py` on the clip -- but read its DISAGREEMENTS
   and the reader's own cells at the slots around the picture, not its
   percentage. Decode those slots with `-frames:v` capped (an uncapped `trim`
   printed 501 tiles and an off-by-one that was the probe's, not the clip's).
3. Hop 6: `tools/probe_clip_seek.py --attempt N --slots a-b` around the
   picture. If Chrome presents slot k-1 for the old seek meant for k and the
   corrected seek presents k, the fault is the clip's first pts and the
   panel's slot arithmetic, and no reader fix can hold. `ffprobe -show_frames
   -read_intervals` prints the pts themselves when the probe's numbers need
   a second witness.

## Failure catalogue

- 2026-09-01 hop 2 — "frame 0 is before the reset... frame 3 is the first frame I actually reset on" — the run ended at the first grab ACTION (a midair fall), so `first` landed four frames before the reset press — fixed in `track.py` (the dance's first frame ends the run; the fall is timed).
- 2026-09-01 hop 7 — "84 2 on screen, 84 in our tool, yet screen-checked 100%" (5782) — the map is RIGHT (slot 496 = frame 157 = R2, sharp minimum at shift 0); Chrome presents slot k-1 for the timeline's seek to k because the clip's first pts is 0.011 s (2/3 of a slot) and the seek targets `(k+0.5)/60`; the panel then reads the presented frame honestly and shows the earlier pad — fix belongs at hop 6 (zero the video's first pts at extraction, and carry `start_time` to the panel for older clips), never in the reader.
- 2026-09-01 hop 5 — the METER: `score` counts the objective `align` minimised, so it returns the same number for a correct map and one corrupted by +2 inside an evidence-free hold (fresh-context review, T1). An honest meter reports agreement, COVERAGE (the display can distinguish only ~17% of frames from a neighbour — holds dominate) and EXPOSURE (the longest unpinned run), computed against the map the reader did NOT align.
- 2026-09-01 hop 4 — the structural finding: one video frame per distinct captured picture, stamped with the ledger's RAM frame at encode time, would make the map an identity plus one offset (item 38's approved recorder change, never built). Everything downstream is recovering an identity capture threw away.
- 2026-09-01 hop 6, the FIX itself -- `tools/probe_clip_seek.py` shipped and its first run on 5782 printed `first video pts 0.000000` with the corrected seek still one early: `video_start_of` built the ffprobe path by replacing `ffmpeg` in the whole path, which renamed the install folder (`D:/ffmpeg/bin/ffmpeg.EXE` -> `D:/ffprobe/bin/ffprobe.EXE`) and fell to the 0.0 fallback -- the shipped fix would have changed nothing on his machine. Fixed by file-name replacement + PATH fallback (`ffprobe_beside`). The lesson is the one the probe column exists for: a fix at the right hop still needs its probe run against it, because a fallback that returns the old assumption is indistinguishable from the fix working on a clip that never needed it.
- 2026-09-02 hop 4, BUILT -- item 38, the recorder change he approved: the ring holds one video frame per distinct captured picture at its own time. Three measurements shaped it, each a way the obvious version was wrong: ffmpeg's `-use_wallclock_as_timestamps` stamps at its READ, and its scheduler reads a pipe in bursts, so a 30 pictures/s feed came out with 108 frames of one segment ONE 90 kHz TICK apart; a wall-clock-stamped audio pipe beside a stamped video stream throttled the video to 26 of 30 pictures/s whatever offset the two carried (lag +-2 s, no filter, null output: all 26; no audio: 30); and `-fflags +nobuffer` discards the packets stream analysis reads (23 of the first 83 pictures). The shape that measured clean: one NUT stream on stdin carrying video AND audio with this process's own stamps, `-fps_mode passthrough -enc_time_base demux`, per-segment timestamp reset off. Proof: sink -> ring -> cut -> feed map, 151 of 151 pictures, 0 unmatched, residual 0.15 ms median / 2.1 ms max; a flash and a click at one instant land together in the cut.
- 2026-09-02 hop 5, the pad reader's DECODE AXIS -- "basically every single frame is wrong" on a picture-feed clip (5814): the panel lagged the screen by a uniform ~2 game frames, and the reader's own screen-reads and its disagreement flags were wrong too. First divergence at hop 5 (fresh-context review, counterfactual: forcing the correct decode moved screen-vs-map agreement from +2 to 0 and 61% -> 96%). `padread.decode_cells`/`decode_icons` ran ffmpeg WITHOUT `-fps_mode passthrough`, so a VFR picture-feed clip (r_frame_rate 120) was re-timed onto its rate grid and 8 frames duplicated: 726 cells of a 718-frame clip. `read_clip` kept the first 718, every cell past the first dup shifted, and that sheared path was written back as the map. Fixed by decoding passthrough (one flag), so the reader's cell axis IS the clip's frame axis IS the browser's slot axis. The picture feed was NOT the fault and was NOT reverted. Also fixed: the ffprobe-path whole-string replace recurred here (`_clip_dims` now uses `ffprobe_beside`), and `tools/inspect_timeline.py` was CFR-blind (it read a VFR clip on a /60 grid and faked a ~55-frame stamp gap; now seeks via frame_times).
- 2026-09-02 hop 5, DUPLICATE PICTURES -- "seems like we're still struggling with duplicate frames in the video... Ideally when the user plays back their video, they NEVER see a duplicate frame." A picture-feed clip holds one encoded frame per CAPTURED picture, but when the game lags the emulator re-presents the same render: two grabs, two ledger rows with ADVANCING RAM stamps, one picture on screen. Measured on his pyramid clip (5946): 115 of 775 stored frames pixel-identical to their predecessor, and the map stepped +1 across 110 of them -- the panel's pad changed while the screen held, and the stepper landed on the same image twice. Root cause of the flag that should have stopped it: `padread.picture_flags` unpacked `picture_runs`' `(first slot, LENGTH)` as `(start, end)`, so `same[start + 1 : end + 1]` was an EMPTY slice for any run past the clip's opening -- the aligner's "may only dwell" constraint reached almost nothing. Fixed three ways, each measured: the run-length unpacking; `mapalign.decode_grey` decodes `-fps_mode passthrough` like the reader's (a VFR clip's runs must index the clip's own frames); and the picture runs are applied AGAIN after the reader answers, so one answer per picture is an invariant of the SHIPPED map rather than a hope about the reader. After: 115/115 duplicates step 0, 115/115 show their predecessor's pad, and the stepper can land on 0 of the 115.
- 2026-09-02 hop 4, TWO CUTS ONE PATH -- his 100-coin replay played as a black video: the H.264 stream was full of invalid NAL units and the sidecar counted 1921 frames of a file holding 1380. He clicked extract and the LBLJ autodetect re-opened the drawer, so two `view()` calls raced: `view` checked `clip.exists()`, both missed, and two ffmpeg processes wrote one output path. Fixed twice over -- `ReplayService.view` takes a per-attempt lock (the second caller waits and takes the cached clip), and `ClipExtractor.extract` cuts to `<name>.cut<pid>.mp4`, probes THAT file, and `os.replace`s it into place, so a partial or racing write can never be served and the sidecar can never describe a different file than the one on disk. The temp name keeps the .mp4 suffix LAST: ffmpeg picks its muxer from the extension.
- 2026-09-02 hop 4/5, A LOADED MACHINE -- "I would expect that this system is deterministic / unimpacted by external lag from other sources." Capture is real-time, so a loaded machine genuinely produces FEWER pictures: his Haunted Books clip captured 680 pictures, encoded 387 (20.4/s against ~30; the rest dropped at the sink's PICTURE_QUEUE) and the feed log then matched only 178 of 387, so `feed_map` refused and the clip shipped with NO frame map -- the panel fell back to plain arithmetic, which is "lots of incorrect frames". Fewer frames is honest; no map is not. The picture-ledger path now answers when the feed log cannot: it matches rows to the clip's own picture RUNS, which does not care how many frames went missing, and it is handed the clip's own `frame_times` (a VFR clip's runs never sit on the 60 Hz grid -- the third instance of that blindness). What is still owed: the drops themselves (a bigger queue, or a lower grab rate under load) and an honest surface saying the capture was degraded.
- 2026-09-02 hop 4, CAPTURED AND ENCODED IN LOCKSTEP -- his rule: "We should always be encoding frames we captured. I don't understand why lag means we don't encode the frames? If I see a frame in my replay, as a user, I would expect to see the input capture for that frame as well." He is right, and the old shape was indefensible: the sink's queue was 16 pictures deep and shed its OLDEST entry on overflow -- a picture the LEDGER HAD ALREADY RECORDED -- so under load the ledger described frames the video did not contain and the feed log could no longer cover the clip (his Haunted Books run: 680 captured, 387 encoded). Now the recorder asks `sink.has_room()` BEFORE `ledger.observe`, so a picture it cannot encode is never recorded as captured; the queue is bounded by BYTES (512 MB, ~65 of his frames, >2 s of slack) and drops nothing once queued. A loaded machine yields a sparser clip, never a clip whose map is a lie. `grabs_skipped` and `encode_backlog` ride `/api/replay/status`, so "this capture was degraded" is a number rather than a thinner-looking video.
- 2026-09-02 hop 5, THE READER IS AN AUDITOR, NOT AN ALIGNER (on a covered clip) -- his "if even ONE frame is wrong, that's unacceptable", against single-frame BUTTON errors in neutral stretches (Elevator Tour frame 13 drew R where the screen showed Cdown). A fresh review measured what the per-slot DP does: 50-77% of a clip's frames repeat their predecessor's pad, so the display cannot separate them, and 78-94% of the slots the DP MOVES off the feed log sit between two such frames -- unfalsifiable moves, and the source of the run-to-run flakiness. On the two clips whose feed log covered them (92%, 100%), the bookkeeping plus ONE flat integer equalled a HINDSIGHT per-window corrector and came within 0.3 and 0.5 points of the DP; on a 73%-covered clip the DP genuinely earned 10 points. So `feed_match.matched / frames` decides: >= 0.85 (and a sweep margin >= 0.15) ships `feed_log+offset` and the reader only reports; below, the DP aligns as before and the clip is marked `frame_map_degraded` so a repaired capture never looks like a clean one. The offset comes from a direct sweep over [-6, +6] of screen agreement (`padread.offset_sweep`) against the map the reader was HANDED -- no DP, not circular, and its margin is its own refusal criterion. RULED OUT in the same review: learning more button-icon templates. Press edges resolve only 3-10% of the ambiguity, because a held stretch is usually idle on the buttons too.
- 2026-09-02 hop 5, THE READER'S OWN COMMONEST MISREAD, invisible for the whole feature -- his question was the right one: "have we even FOR SURE confirmed that we can even accurately extract the numbers... out from the bottom left corner of the screen?" No, and it could not: every accuracy number was scored against a map the reader itself aligned. THE MAP-FREE TEST is the display's own GRAMMAR -- Usamune prints an axis as a bare `0` (blank letter, `0`, blank) or a letter beside a magnitude of 1..99, so a letter beside magnitude 0 is impossible with no map and no threshold involved. Measured on his Shoot into the Wild Blue clip (6510): **563 of 6316 axis-readings, 8.9%, were exactly that**. Cause: `ink_mask`'s `bright` clause counts any bright pixel as font ink, so a blank cell over a WHITE SKY is all ink and the silver U -- mostly white highlight -- matches it at distance 38 with a wide margin. Two consequences, both of which he reported: the disagreement list filled with false accusations against the timeline ("a lot of the screen checked frames aren't actually even wrong" -- 578 of that clip's 604 were the reader's own misread), and the aligner paid a unit for the letter at EVERY candidate frame in exactly the resting stretches where it has the most freedom, which is where his single wrong BUTTON frames appear. `padread.enforce_grammar` corrects it: impossible on his clip 8.9% -> 0.00%, agreement 80.8% -> 99.17%, misreads 595 -> 17, disagreements 604 -> 26. STILL WEAK, not the map's problem: with better letter reads the icon channel learns more buttons and agrees on only 760 of 1557 lit icons (it was A-only at 99%) -- a false-positive icon reader, same bright-background family; measured to change the alignment on that clip by NOTHING (icons on and off give identical maps), so it is a reporting weakness, not a correctness one. And `ink_mask`'s bright clause is the underlying cause of both and is still there; the grammar is a guard above it.
