| Replay orchestration (attach loop, source wiring, ring, idle gate) | `replay/recorder.py` + player-input tap `replay/activity.py`; `replay/clock.py` is THE QPC↔UTC contract. | THE PAD READER -- Usamune's input display read out of a clip's pixels | `replay/padread.py`, an OFFLINE INSTRUMENT since 2026-09-05, not part of extraction. Six glyph cells per picture (letter/d1/d2 on the U-D line and the L-R line), one template per painted GLYPH weighted to the pixels the font paints (`ink_mask`) where the exemplars agree; a cell reads only by a clear margin (`DIST_MAX`/`MARGIN_MIN`) else it is UNKNOWN -- there is no blank class, so an empty cell can never be read as a glyph. A shipped reference alphabet (`data/pad_glyphs_us.npz`, learned off 7 min of ring footage and verified against the track) reads first, then the clip re-learns its own glyphs at its own scale. `enforce_grammar` fixes its commonest error, found map-free: Usamune prints an axis as a bare `0` or a letter beside 1..99, so a letter beside magnitude 0 is impossible -- 8.9% of readings on clip 6510 were exactly that, because `ink_mask`'s bright clause counts a white sky as ink. WHY IT LEFT EXTRACTION: it answered "does the timeline hold the pad the game held", which the capture layer's own copied pad answers exactly and for free, and it answered it at 82-94% on three clips the oracle certified exact -- every sampled disagreement its own digit confusion (L13 for L12, U83 for U82, a dropped letter). At extraction it was also reading almost nothing (65 of 477 cells on 7267) while costing ~3 s a clip. WHY IT STAYS: `tools/score_pad_read.py` and `tools/score_picture_offset.py` are the instruments that settle a picture-vs-pad question, `replay/oracleread.py` borrows its glyph machinery, and reading the pad off PIXELS is how CONSOLE input capture would work, where no RAM is readable. |
| THE CAPTURE LAYER (round 32 item 95, 2026-09-04): recording frames that ARE game frames | `plugin/gfxwrap/gfxwrap.c` is a wrapper graphics plugin for Project64 1.6 (Zilmar 1.3; `zilmar.h` holds the spec, `stream.h` the shared-memory layout): it forwards everything to the user's own plugin (`wrapped=` in `sm64_trainer_gfx.ini`), copies the tracker's ADDRESS TABLE out of RDRAM at ProcessDList (that list IS frame N: gGlobalTimer still reads N, the pad is N's) and, at the VI whose VI_ORIGIN changed, reads GL_FRONT itself when the emulation thread holds a context, else through the wrapped plugin's own ReadScreen -- GLideN64_LINK_4.2 renders on a thread of its own (measured 2026-09-05 through the host driving the real DLL), so for him it is always ReadScreen: a command that render thread runs after the swap, its buffer freed through HeapFree once HeapValidate says the static CRT put it on the process heap (STATUS_READSCREEN in the header says so) -- publishing (picture, stamp) into THE FRAME STREAM (`replay/framestream.py`, one mapping + one event, a 3-slot ring). The plugin knows NO game address -- the table comes from the live layout (`replay/pluginsource.py::table_for`), so `memory/layout.py` stays the one source. `PluginVideoSource` decodes a slot's bytes with the sampler's own `inputs/frame.py::decode` over a `RegionMemory` (PJ64 word order, the same swap rules as `memory/base.py`) and calls `recorder._on_frame(bgra, ts_100ns, stamp)`; the recorder tags the picture with the STAMP's frame (the frame clock is not asked) and the ledger row says `exact`. `ReplayService._map_from_feeds` joins such rows to the clip's pictures as stamp - `PLUGIN_PICTURE_LAG` (1: the grabbed picture IS the list before the one just stamped -- SM64 presents the buffer it rendered the iteration before -- measured 2026-09-05 by the oracle on 7049/7090/7116: the printed gGlobalTimer equals stamp - 1 on 1863 of 1864 readable slots, 0 contradicted; the desktop grab's `DISPLAY_LAG_FRAMES` is a different camera's fact) and `None` on an inexact row, and `_take_the_stamps`: every row exact -> the map IS the rows (`frame_map_source: plugin`), `picture_igt` = the stamped IGT per slot (the inspector's clock), and `_audit_pad_stamps` compares the stamp's pad with the input track's (`pad_stamp_agreement`, no pixels) -- the clip's one shipped check, SILENT when it passes: only a disagreement draws a chip on the timeline's header (2026-09-05, his ruling on the passing state: "worthless information for them"). Rows that are NOT all exact leave the clip with no map at all. `main.py` opens the stream at boot, writes the table, and picks the plugin source per attach when the heartbeat moves within 0.2 s AND `pluginsource.pictures_flow` sees a first picture within 0.6 s -- otherwise `DesktopUntilLayerPresents`: the desktop grab watching the heartbeat once a second, which ends itself like a lost window the moment a picture flows so the attach loop's next factory call gets the plugin (the recorder attaches to PJ64's window before the ROM runs, and the order he opens things in must not matter -- 2026-09-05), with the reason on `/api/replay/status` `frame_source_note` while a loaded layer refuses (asked again every 15 s; a layer whose heartbeat moved while it refused every picture held an empty ring for an hour). `CaptureLayer.refresh_if_stale` copies a newer build's DLL over the installed one at boot while PJ64 is closed; the setup screen's row shows its problems and an Update button otherwise. THE ORACLE (`replay/oracleread.py`, `tools/score_oracle.py --attempt N`): the frame number Usamune's HUD memory display of 0x8032D5D4 prints into the picture, read map-free through the +1 rule (a value counts only when a neighbour vouches for it; near-identical duplicate pictures allow 0; a digit-count guard drops truncated reads; bridged predictions are verified box by box; the reference alphabet `data/oracle_glyphs_us.npz` was learned off his three oracle clips 6650/6702/6678, kept under `replays/oracle/`). | The picture feed and retained media clock | `replay/media.py::MediaRun` owns encoder identity/origin. `ffmpeg_sink.py` assigns monotonic 90 kHz video PTS, trims pre-origin audio, preserves NUT -> TS timestamps and records the assigned PTS in `ledger.py`; segments retain their run. `extract.py` cuts with the same integer offset, disables timestamp shifting, uses 90 kHz MP4 edit lists, and returns `source_pts` plus browser `frame_times`. `feedmap.py` looks up exact source keys; no cadence/bias fit is allowed. `tests/test_replay_picture_identity.py` independently decodes painted picture IDs across encoders, fractional cuts, queued audio, stalls and timestamp collisions. | The PICTURE LEDGER (item 40 — capture's own per-picture record, the map's FIRST source) | `replay/ledger.py` — his spec 2026-08-28: "at every single frame of gameplay we have access to all the memory addresses and data in-game… embed each frame with extra information… extend the frame-by-frame information storage at any point". `recorder._on_frame` passes every grab to `PictureLedger.observe`, which dedups by EXACT equality of a stride-8 sample (pre-encode grabs of one presented picture are byte-identical; 93 µs/grab measured at 1600×1224, ~1.1% of a core at 120/s) and records one row per DISTINCT picture: composition time, RAM frame, plus every registered stamp (`ledger.stamps["name"] = callable` — ONE line extends the record). At extraction the clip's slice of those rows becomes the sidecar's `picture_ledger` — the durable per-frame record, stamps included — and `feed_map` joins it to the encoded frames. `observe()` never raises, so a ledger bug cannot cost capture. Torn grabs (a mid-update surface copy; 118 of 647 row gaps under 20 ms on attempt 4518) fold into their present row via `MIN_ROW_GAP_S`. **Debugging ANY timeline-vs-video report starts with `tools/inspect_timeline.py`** (item 44): `--frames` prints, per panel frame, the track pads, the map's slots and the ledger rows with their stamps; `--audit` walks the whole clip (row rate, torn pairs, stamp-vs-map residual stretches). The panel's FRAME readout is 0-based = the track axis |
| A+V single mux (ffmpeg subprocess) | `replay/ffmpeg_sink.py::FfmpegAvSink` — ONE ffmpeg muxes video (stdin) + audio (named pipe) on ONE wall-clock: `-use_wallclock_as_timestamps` before each input, `-fps_mode cfr` video, `-af aresample=async=1` audio → combined A+V MPEG-TS segments. THIS is the two-clock-drift fix (memory `replay-av-drift-two-clocks`); feeder pacing is not load-bearing. Segment→UTC = anchor-at-first-frame + CSV offset RELATIVE to the first segment. In-process fallback (no ffmpeg, legacy two-clock): `replay/encoder.py`. Encode QUALITY comes from `replay/config.py::video_quality_args`, not here |
| GC policy (stop-the-world watchdog + gen-2 idle collector) | `replay/_gcwatch.py` — freezes the startup heap, disables AUTO gen-2, runs manual `gc.collect(2)` during idle with a 5-min never-idle backstop; `arm(is_idle=recorder.is_idle)` from `server/app.py` lifespan |
| Audio (per-process tap primary, endpoint-by-pid fallback, RT-safe pump, deaf-stream watchdog) | `replay/audio.py` + `replay/_system_audio.py` — `ProcessAudioSource` (proctap / WASAPI **process** loopback) is PRIMARY so a clip carries the game and nothing else on the desktop; `SystemAudioSource` (device loopback of the endpoint hosting the pid's session) is the FALLBACK and records everything sharing that endpoint. Both factories take the **pid** (`recorder.py`), both feed the same `AudioPump` — a PURE RT-safe handoff (PCM → `recorder._on_pcm` → sink's audio pipe; no sample-count placement / silence injection, ffmpeg's wallclock+aresample own timing) — and both self-heal through the shared `DeafStreamWatchdog`. proctap yields float32; int16 is the one format on the wire to the sink. `proctap` must stay in `tools/build_exe.py::COLLECT` or the frozen exe silently degrades to desktop-wide capture. **`tools/probe_audio_isolation.py` is the live gate**: two ffplay children playing 440/880 Hz at once, only the 440 process captured — one tone proves the tap is alive, never that it is isolated (device loopback passes a one-tone test perfectly). Rejected alternatives and the deaf-tap escalation policy: docs/architecture.md audio facts |
| Clip extraction (ffmpeg cut of A+V segments) | `replay/extract.py` — pure ffmpeg cut: `concat:` the covering segments, accurate-seek the span, re-encode video (0.5s GOP) + faststart, `-c:a copy`. Coverage holes clamp to the contiguous run containing the span start (`contiguous_run` / `_joinable` — a FRAME-SIZE change breaks a run too). Segments carry their `dims` (`SegmentInfo`, stamped per ffmpeg child). Quality from `replay/config.py::video_quality_args` — the cut must be TRANSPARENT w.r.t. its segments |
| Encode quality (ring sink + clip cut) | `replay/config.py` — `VIDEO_CQ`/`VIDEO_CRF` + `video_quality_args(codec, stage, maxrate)`, THE registry both encoders read. Raising quality costs ring disk — `VIDEO_CQ` is the one knob |
